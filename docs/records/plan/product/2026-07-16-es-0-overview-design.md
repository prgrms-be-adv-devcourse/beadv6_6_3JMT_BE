# ES 검색·추천 설계 0 — 개요·확정 결정·문서 맵

> Prompthub 상품 검색·추천을 Elasticsearch 9.x로 구축하는 설계의 입구 문서.
> 상세는 1~7번 문서로 나뉘며, 이 문서는 전체 그림과 확정된 결정만 담는다.

## 목표

프롬프트/파일템플릿(PPT·EXCEL)/외부링크(NOTION)를 파는 마켓플레이스의 상품 검색과 추천.
행동 데이터가 없는 콜드 스타트에서 시작해, 검색·클릭·구매 로그가 쌓이면서
개인화·의미 기반 추천으로 발전한다. 한글(nori) + 시맨틱(의도) 검색이 핵심.

## 확정된 결정 (결정 로그)

| # | 결정 | 근거 요약 |
|---|---|---|
| D1 | 모듈러 모놀리스 — product-service 한 서비스 안에 search/recommendation 패키지 추가 | EC2 배포 자원 부족. 분리 여지는 패키지 경계로 확보 (문서 6) |
| D2 | ES 배포 위치 미정, 로컬 docker-compose(단일 노드)로 개발 우선 | 앱은 ES URL 설정값만 봄 — 나중에 k8s pod든 EC2든 코드 무변경. 설계는 "단일 노드·heap 1GB 안팎" 전제 |
| D3 | **A안: 전부 이벤트 기반, Logstash 없음** — 상품·행동 데이터 모두 Kafka → 자체 컨슈머 → ES | 팀 컨벤션("상태 변경=Kafka 발행") 일치, ES 다운 시 유실 없음, 서비스 분리 대비. Logstash는 별도 JVM(~1GB)이라 자원 낭비 + 우리 이벤트는 이미 구조화된 JSON이라 강점을 못 씀. Kibana는 유입 경로 무관하게 언제든 연결 가능("나중에 ELK" 보장), Logstash도 나중에 kafka input으로 끼울 수 있음 |
| D4 | 임베딩: OpenAI `text-embedding-3-small` (1536차원) | 비용 극소($0.02/1M토큰 — 상품 수천 개 색인 수십 원, 검색 10만 회 ~$0.03). 인프라 불필요. 차원이 확정되어 매핑을 처음부터 고정 가능 |
| D5 | 설계는 전체, 구현은 Phase 1(lexical) → 2(시맨틱·자동완성) → 3(행동로그·개인화) | 문서 6의 로드맵 |
| D6 | 행동 로그 퍼널: FE 최소 훅(searchId 쿼리파라미터) + last-touch 어트리뷰션 | 클릭 출처는 브라우저만 앎. order-service는 무변경(기존 order-events 재활용) |
| D7 | 하이브리드 결합은 앱에서 RRF 직접 계산 (msearch 두 레그) | ES 내장 RRF retriever는 유료(Platinum). BM25·코사인 점수 단위가 달라 점수 덧셈은 튜닝 지옥 — 등수 기반 RRF가 표준 |
| D8 | 찜(wish) 신호: **계약만 확정, 구현은 user-service 합의 조건부** | wish_count는 미구현 컬럼(항상 0). 채우려면 user-service가 user-events 발행 필요 = 팀원 작업. 계약서는 문서 5에 확정해두고, 합의되면 켠다. 없어도 인기순·개인화 모두 성립 |
| D9 | 자모/초성 변환은 ES 플러그인이 아니라 앱 코드 전처리 | 한글 초성 플러그인은 ES 9.x 미지원(방치 상태). 앱 전처리는 유닛 테스트 가능, 플러그인은 nori 하나로 끝 |
| D10 | ES 문서는 family당 1개, `_id` = familyRootId | row-chain 버전을 검색에 노출하지 않음. 버전 교체 = 덮어쓰기, 중복 노출 원천 차단 (문서 1) |
| **D11** | **공개 API의 주체는 product 단독** — search/recommendation에 컨트롤러를 두지 않는다 | recommendation은 추천 로직 단위이지 API 주체가 아니다. #377이 이미 포트 호출 방식으로 구현·검증했다. 원안(문서 6 §1·§2)의 컨트롤러 이관을 폐기하고 의존 방향을 `product → search/recommendation`으로 뒤집는다. 서비스 분리 비용 증가는 명시적으로 수용 (2026-07-27) |
| **D12** | **임베딩은 Postgres(pgvector)가 원본, ES는 검색용 복사본.** 비슷한 상품 추천은 Postgres에서 직접 조회 | ES 유실 시 임베딩 재생성이 외부 API 재호출을 요구해 "ES는 재구성 가능한 사본" 전제가 깨졌다. 추천을 Postgres로 옮기면 색인 지연(최대 20초)·ES 장애와 무관해지고 폴백 이중 경로가 사라진다. 하이브리드 검색은 RRF가 두 레그를 한 시스템에서 병합해야 하므로 ES 사본을 유지. 대가는 커스텀 Postgres 이미지(공유 인프라) (2026-07-27) |

## 범위 변경 (2026-07-27)

| 항목 | 상태 | 사유 |
|---|---|---|
| 자동완성(#379) | **축소** — `match_phrase_prefix` 1회 + `salesCount desc` | 자모·초성·오타교정 제외. prompthub는 사용자가 상품명을 모르는 "의도 검색" 서비스라 초성 검색은 발동 상황이 없다. 되살릴 조건은 #379 본문에 기록 |
| 인기 검색어·검색 히스토리(#382) | **보류** | 최근 검색어는 브라우저 autofill이 이미 제공. 인기 검색어는 집계할 트래픽이 없다. 검색 이력은 #381이 이미 수집하므로 보류로 유실되는 데이터가 없다 |
| 개인화 홈 추천(#383) | **중단** | 행동 데이터 없이는 콜드스타트 폴백(인기순)으로만 동작. 취향 벡터·다양성 규칙은 검증할 수 없는 로직으로 남는다 |
| admin ON_SALE 아웃박스 | **미진행** | 재조정 배치를 증분으로 전환해 폴링 비용이 사라져(조회 2건/사이클), 남는 이득이 "지연 20초 → 즉시"뿐 |
| 재조정 배치 | **증분 전환** | family당 4쿼리 N+1 + 변경 없이도 전체 재작성하던 것을 변경분만 처리로. 주기 20초는 유지하되 근거를 신규 기록 |

## 전체 아키텍처

```
                         product-service (모듈러 모놀리스)
  ┌─────────────────────────────────────────────────────────────────┐
  │  product (기존)          search (신규)         recommendation    │
  │  RDB 원본·row-chain      ES 색인·쿼리·suggest   비슷한상품·개인화  │
  │      │ Kafka 발행            │                      │ SearchPort │
  └──────┼──────────────────────┼──────────────────────┼────────────┘
         ▼                      ▼                      │
   product-events ──────→ 색인 컨슈머 ──→ ┌─ ES ────────▼──────────┐
   behavior-events ─────→ 로그 컨슈머 ──→ │ products (검색 사본)    │
   order-events(기존) ──→ 구매 번역   ──→ │ behavior-logs (data     │
   user-events(조건부) ─→ 찜 반영     ──→ │  stream + ILM)          │
                                          │ search-keywords /       │
   OpenAI 임베딩 API ←── 색인·검색 시     │ user-profiles /         │
   Redis ←── 쿼리 임베딩 캐시·최근검색     │ search-quality-daily    │
                                          └─────────────────────────┘
   원본은 항상 RDB. ES는 전부 재구성 가능한 사본 (풀 리인덱스 배치).
   ES 장애 시 검색·목록은 기존 RDB 조회로 폴백.
```

## 스코프 제외 (추후 아이디어로만 기록)

- **찜 신호 활성화** — 계약은 문서 5에 확정. user-service 발행 합의 시 켠다 (D8)
- **저장된 검색 + 알림** — 알림 인프라 부재. 개인 최근 검색어(Redis)까지만 구현
- **파일(PPT/EXCEL) 텍스트 추출 색인** — 매핑에 `extractedText` 자리만 예약
- **NOTION 외부 원문 색인** — 권리·안정성 문제로 셀러 입력 메타만 사용
- **함께 산 상품(co-purchase), LTR, A/B 테스트** — 행동 데이터 축적 후 별도 설계
