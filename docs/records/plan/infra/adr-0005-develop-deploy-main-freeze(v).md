# ADR-0005: 배포는 develop 머지에 직결하고, main은 완성 스냅샷 보관 브랜치로 동결한다

- 상태: accepted
- 날짜: 2026-07-07
- 관련: `.github/workflows/cd-selfhosted-compose.yml`, `.github/workflows/ci-main.yml`,
  `docs/records/plan/infra/adr-0004-centralized-config.md`(설정 반영 시점이 이 결정의 CD에 연동),
  `user-service/.claude/rules/git-convention.md`(환경 정의 갱신 필요)

## 컨텍스트

- **운영(prod) 서버가 없다.** 물리 배포 환경은 AWS EC2 인스턴스 하나뿐이며, 이 인스턴스의
  명칭을 "운영 서버"에서 **"개발서버"**로 바꿨다. 이름만 바뀐 게 아니라 역할이 바뀐 것이다 —
  안정 운영 대상이 아니라 팀의 공유 통합 환경이다.
- 기존 CD는 **main 푸시 → EC2 self-hosted 러너가 변경 모듈만 빌드·compose 교체**였다.
  main = 운영, develop = 통합이라는 2단 승격 전제였는데, 서버가 하나뿐이면 develop → main
  승격은 아무것도 검증하지 않는 빈 의식이 되고 반영 지연만 남는다.
- 프로젝트는 두 단계다: **세미 프로젝트**(완료, API 경로 `api/v1`)와 **최종 프로젝트**
  (진행 예정, `api/v2`로 재구현). 세미 프로젝트의 완성 상태를 보존할 방법이 필요하다.
- 팀은 머지 전 로컬 docker compose 통합 검증 환경을 운영하지 않기로 했다(운영 부담).

## 결정

### 1. CD 트리거를 main에서 develop으로 **교체**한다 (추가가 아니다)

PR 승인 → develop 머지 → 개발서버 자동 배포. 변경 모듈만 새 이미지로 교체하는 현행 감지
방식은 유지하고, `configs/` 파일명→서비스 매핑 재시작을 추가한다(ADR-0004 — native 채택,
git 백엔드·라벨 미사용).

**main 트리거는 반드시 제거한다.** 남겨두면 아래 3번의 "최종 develop→main 머지" 순간에
의도치 않은 배포가 한 번 더 발생한다.

### 2. 검증 공백은 수용하고, 빠른 복구를 원칙으로 한다

로컬 compose 폐지로 "머지 전 전체 기동 검증" 층이 사라졌다. Eureka 등록·config server
배선·Kafka 연결처럼 떠봐야 아는 오류는 이제 **머지 후 개발서버에서** 드러난다.
개발서버는 운영이 아니므로 잠시 깨지는 것을 허용하되:

- 배포 후 각 서비스 `actuator/health`를 확인한다 (머지한 사람의 책임).
- 깨졌으면 원인 수정보다 **revert PR을 먼저** 올린다 — revert 머지가 곧 재배포 트리거다.

### 3. main은 동결하고, 태그 2개 + 최종 머지 1회만 남긴다

- **지금**: main HEAD(세미 프로젝트 완성 상태)에 `v1.0.0` 태그를 단다. main으로의 일상
  머지·직접 작업은 금지.
- **최종 프로젝트 완료 시**: develop → main **머지 1회** 후 main에 `v2.0.0` 태그.

"main은 태그 관리만 한다"는 절반만 맞다 — 태그는 브랜치가 아니라 커밋에 붙으므로, 최종
태그를 main에 달려면 마지막 머지 1회가 필요하다. 이 머지로 main은 "완성 스냅샷 보관
브랜치"라는 관례적 의미(main = 최신 완성본)를 유지한다.

`ci-main.yml`(main 대상 PR 검증)은 이 최종 머지 PR 1회를 위해 남겨둔다.

## 검토한 대안

1. **현행 유지 (main 배포 + develop→main 승격)** — 서버가 하나라 승격 단계가 검증 없는
   요식이 됨. 기각.
2. **main 완전 동결, 태그를 develop 커밋에 직접** — 머지 작업이 아예 없어 단순하지만,
   main이 세미 프로젝트 상태로 영구 고정된 죽은 브랜치가 되고 "main = 최신 완성본"이라는
   관례적 기대와 어긋남. 기각.
3. **로컬 compose 검증 유지 + develop 배포** — 검증 공백은 없지만 팀이 로컬 통합 환경
   운영 부담을 이유로 폐지를 결정. 기각(개발서버가 불안정해 공유 작업이 자주 막히면 재검토).

## 결과

- **머지 = 배포**가 된다. develop 머지 빈도가 높은 기간에는 self-hosted 러너에 배포가
  연속으로 큐잉되므로, CD 워크플로에 `concurrency` 그룹(진행 중 배포 취소 또는 순차화)
  설정을 권장한다.
- 롤백 수단은 revert PR로 일원화된다. main이 더 이상 "안정 버전"이 아니므로 "main으로
  되돌려 배포"라는 선택지는 없다. 필요 시 `v1.0.0` 태그가 마지막 안정 스냅샷 역할을 한다.
- 개발서버는 develop의 진행 중인 코드(api/v2 작업 포함)를 서빙한다. **api/v1은 태그로만
  존재하고 어디에도 서빙되지 않는다** — 세미 프로젝트 시연이 다시 필요하면 태그 체크아웃
  기반 수동 기동이 필요하다.
- 설정 반영 경로가 이 CD에 얹힌다: `configs/` 변경도 develop 머지 → config 재빌드·재배포 +
  해당 서비스 재시작으로 반영된다(ADR-0004 — native 채택, 라벨 미사용).
- stale해지는 문서: `user-service/.claude/rules/git-convention.md`의 "개발 환경: prod —
  운영 / dev — 개발" 항목, `docs/api-spec/*`의 `api/v1` Base 경로(v2 전환은 별도 작업),
  `config/CLAUDE.md`. 마이그레이션 5단계(문서 동기화)에서 함께 정리한다.
- 재검토 트리거: 운영(prod) 서버가 실제로 생기면 main을 배포 브랜치로 복권하고 2단 승격
  (develop=개발서버, main=운영)을 복원한다 — 그 구조는 ADR-0004의 개정 전 이력에 남아 있다.

## 현황 업데이트 (2026-07-22)

- **문서 자체의 결함을 정리함**: 이전 버전은 본문(컨텍스트~결과)이 병합 사고로 통째로
  두 번 중복 저장돼 있었다. 내용 변경 없이 중복만 제거.
- **api/v1 → api/v2 전환이 이미 완료됨**: `grep` 기준 `/api/v1` 매핑 0개, `/api/v2` 전면
  사용 — "api/v1은 태그로만 존재" 서술이 현재는 정확히 들어맞는다.
- **CD가 compose에서 Kubernetes로 실질 전환 중**: `cd-selfhosted-kubernetes.yml`이
  `push: [develop]`로 활성화됐고, 이 문서가 다루는 `cd-selfhosted-compose.yml`의 develop
  push 트리거는 주석 처리되어 수동(`workflow_dispatch`)으로만 남아있다. "머지 = 배포"라는
  이 ADR의 핵심 결정은 트리거 대상이 compose→k8s로 바뀌었을 뿐 원칙 자체는 유지되고 있으나,
  이 전환을 기록하는 별도 ADR이 아직 없다.
- `ci-main.yml`에 이 문서가 언급하지 않는 `push: [infra]` 트리거가 추가되어 있음 — `infra`
  브랜치의 용도를 이 ADR 또는 별도 문서에 기록할 필요.
