# 서비스 간 통신 경계 — 내부 gRPC 남용에서 화면 조합(프론트 다중 호출)으로

> 이 문서는 사후 기록(retrospective)이다. 아래 결정들은 이미 코드에 반영된 뒤 근거 문서가
> 없다는 게 뒤늦게 확인돼 정리했다. 최초 설계 시점에 작성된 문서가 아니므로, 당시 실시간으로
> 검토된 대안 비교나 수치는 존재하지 않는다 — 있는 그대로, 실제 겪은 순서대로 남긴다.

## 배경

서비스를 MSA로 분리했지만, 초기 설계는 서비스 경계를 "각자 자기 데이터만 책임진다"가 아니라
"백엔드가 화면에 필요한 데이터를 전부 상하차해서 내려줘야 한다"는 전제로 그었다. 그 결과 화면
하나를 채우는 데 필요한 여러 서비스의 데이터를 특정 서비스가 내부 gRPC로 서로 끌어와 합성하는
구조가 기본값이 됐다.

## 결정 히스토리

이 문서가 다루는 방향은 한 번에 정해지지 않았고, 아래 순서로 뒤집혔다.

1. **초기: 내부 gRPC로 전부 연결.** 화면 하나에 여러 서비스 데이터가 필요하면, 그 화면을 맡은
   서비스가 나머지 서비스를 gRPC로 호출해 백엔드에서 합성한 뒤 프론트에 하나의 응답으로
   내려주는 방식을 기본으로 삼았다.
2. **문제 발견 계기: BFF 도입을 검토하다가 기존 설계 오류가 드러남.** 뒤늦게 잘못된 부분을
   바로잡으려 설계를 계속 손보는 과정에서 BFF 도입을 검토했고, 이 과정에서 그동안의 서비스 간
   결합 방식 자체가 잘못됐다는 게 드러났다.
3. **AI 검증 실패.** 설계를 반복해서 손보는 동안 AI에게 계속 방향을 물었는데, AI는 "지금처럼
   내부 통신(gRPC)으로 묶는 게 적합하다"는 결론을 계속 냈다. 그 결론이 어떤 추론으로 나온
   건지 캐물으니 근거가 무너졌다 — 실제로는 근거가 있어서 낸 결론이 아니라 그럴듯하게
   합리화한 것에 가까웠다(환각).
4. **실무자 검증: "이럴 거면 모놀리식을 해야지."** 외부 실무자 2명에게 구조를 보여주고 물었더니
   둘 다 잘못된 구현이라고 지적했다. 서비스 간 결합도가 이 정도로 높으면 차라리 모놀리식으로
   가는 게 낫다는 평가였다.
5. **BFF를 실제로 도입하려다 개발서버 메모리 부족으로 좌절.** BFF 자체는 방향으로는 맞다고
   판단해 학습 후 도입을 시도했지만, 개발 서버에 모듈을 하나 더 띄울 메모리 여유가 없었다.
   **이게 BFF를 코드에 도입하지 않은 실제 이유다** — 결합도·트래픽·비용을 저울질한 원칙적
   판단이 아니라 순수한 인프라 자원 제약이었다.
6. **현재: 프론트가 여러 공개 API를 호출해 화면에서 직접 조합.** BFF가 하려던 조합 역할을
   프론트로 넘겼다. 아래 개별 설계 문서들이 이 방향을 도메인별로 구현한 결과물이다.
   - `docs/records/plan/settlement/2026-07-22-wishlist-frontend-composition-design.md`
   - `docs/records/plan/settlement/2026-07-22-order-product-seller-query-design.md`
   - `docs/records/plan/settlement/2026-07-21-seller-settlement-summary-service-boundary.md`

## 회고 — 이 과정에서 겪은 MSA 안티패턴

MSA를 충분히 학습하지 않고(학습 곡선을 건너뛰고) 도입한 팀이 겪는 문제를 거의 다 겪었다.

1. **서비스별 gRPC 라우팅을 먼저 굳혔다가 개발 도중 REST API 스펙을 전부 갈아엎음.** 프론트
   수정 + 백엔드 API 신규 생성 + 기존 gRPC 삭제를 한꺼번에 치렀다.
2. **다른 서비스가 소유한 데이터를 자기 스키마에 테이블로 복제해 들고 있었다.** 서비스 경계를
   무의미하게 만드는 결합이었다.
3. **이벤트 유실 방지에 집착해 "유실 시 gRPC로 다시 받아온다"는 구조만 생각했다.** 실제로는
   Kafka를 쓰면서도 Kafka의 원칙(이벤트는 발행되고, 수신 측이 자기 속도로 쌓아 처리한다)을
   놓쳤다 — 유실을 gRPC fallback으로 메우려는 발상 자체가 이벤트 기반 설계와 맞지 않았다.
4. **컴퓨팅 자원(서버 메모리 등)을 모듈 설계에 반영하지 않았다.** 나중에 메모리가 부족해지자
   원칙과 무관하게 모듈을 합치는 임기응변이 필요해졌다(§결정 히스토리 5번의 BFF 좌절이 바로 이
   문제의 재현이다).
5. **통신(gRPC·이벤트) 스펙을 회의로 정하지 않고, 각자 필요한 데이터를 그때그때 요청하고 응답
   쪽은 의문을 갖지 않고 그대로 구현했다.** 계약이 팀 합의가 아니라 요청자 편의로 누적돼 코드가
   뒤죽박죽이 됐다.
6. **도메인 서비스 간 관계를 다이어그램으로 그리지 않고 AI 구현에 의존했다.** 전체 그림 없이
   부분부분 AI에게 구현을 맡기니 결합 구조를 아무도 한눈에 파악하지 못하는 상태가 됐다.
7. **문제를 인식한 뒤에도 AI에게 계속 물어보는 데 그치고 팀에 공유하지 않았다.** §3의 AI 검증
   실패를 실무자 확인(§4)까지 끌고 가지 않았다면 이 결합 문제는 계속 방치됐을 것이다.

**결론**: MSA 도입은 도메인(팀)별 공통 규칙·설계 회의가 핵심이고, 이 회의는 반드시 산출물을
남기고 그 산출물을 계속 업데이트해야 한다. 그 산출물이 없었던 게 이 프로젝트가 겪은 문제 대부분의
공통 원인이다.

## 지금 원칙 (사후 정리)

- 서비스 소유 데이터 성격의 내부 배치성 조회(예: 정산이 주문의 정산 원천 라인을 당겨오는 경로)는
  gRPC를 유지한다. 기준은 `docs/records/trade-offs/settlement/internal-sync-transport.md` 참고.
- 화면 조합용 데이터는 각 서비스가 공개 REST API로 노출하고, 프론트가 여러 API 응답을 식별자
  기준으로 직접 조합한다. §결정 히스토리 6번의 개별 설계 문서가 이 원칙의 적용 사례다.
- **주의**: 위 개별 설계 문서와 `internal-sync-transport.md`는 이 배경(개발서버 메모리 제약,
  §회고의 안티패턴들) 없이 결과만 마치 원칙적으로 설계한 것처럼 서술한다. 이 문서가 그 공백을
  메운다 — 두 문서를 읽을 때는 "처음부터 이렇게 설계하려 했다"가 아니라 "이 트레이드오프를 거쳐
  이 결과에 도달했다"로 읽어야 한다.

## 프론트가 떠안은 부담 (트레이드오프의 다른 쪽)

BFF/캐시 계층 없이 프론트가 여러 API를 직접 호출해 조합하면서 아래 부담이 프론트로 넘어갔다.

- API별로 다른 실패 정책을 프론트가 관리해야 한다(예: wishlist 설계 문서 §8 — Product 실패는
  화면 전체 실패, Seller 실패는 부분 fallback으로 다르게 처리).
- 여러 호출의 순서·조합(waterfall) 로직이 백엔드가 아니라 프론트 코드에 있다.
- 이 부담을 정량적으로 측정하거나 BFF 대비 비교한 자료는 없다 — §결정 히스토리 5번대로 BFF를
  포기한 이유가 이 부담과의 저울질이 아니라 순수 자원 제약이었기 때문에, 애초에 비교 자체가
  이뤄지지 않았다.
