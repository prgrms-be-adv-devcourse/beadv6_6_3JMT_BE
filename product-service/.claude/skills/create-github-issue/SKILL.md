# Product Issue 생성 Skill

product-service 작업에서 GitHub 이슈 생성을 요청받으면 이 절차를 따른다.

## 1. 이슈 유형 판단

내용을 보고 버그 리포트인지 기능 요청인지 판단한다. 애매하면 사용자에게 묻는다.

## 2. 필수 정보 확인

아래 정보가 부족하면 바로 만들지 않고 한 번에 모아서 되묻는다.

- 버그: 재현 단계, 예상 결과, 실제 결과
- 기능 요청: 문제 제기, 제안하는 기능

## 3. 템플릿 읽기

- 버그: `.github/ISSUE_TEMPLATE/bug_report.md`
- 기능 요청: `.github/ISSUE_TEMPLATE/feature_request.md`

템플릿의 섹션 구조를 그대로 따른다. **frontmatter의 `labels` 값은 참고만 하고 맹신하지
않는다** — 실제 저장소에 그 라벨이 있는지 `gh label list`로 항상 재확인한다.
(`feature_request.md`의 frontmatter는 `labels: feature`지만, 실제 저장소 라벨은 `feature`가
아니라 `feat`이다.)

## 4. 라벨 확인

```bash
gh label list
```

내용 성격에 맞는 실제 존재하는 라벨을 고른다. 매칭되는 라벨이 없으면 라벨 없이 진행한다
(새 라벨을 만들지 않는다).

## 5. 초안 작성 및 승인

title/body/label 초안을 사용자에게 보여주고 승인받는다. 승인 전에는 `gh issue create`를
실행하지 않는다.

**승인은 명확한 긍정 답변만 인정한다** — "네", "진행해줘", "만들어줘"처럼 분명한 승인만
승인으로 간주한다. 슬래시 커맨드 재호출, 화제 전환, 다른 질문 등 애매한 응답은 승인으로
해석하지 않고 반드시 다시 확인한다.

**여러 건을 한 번에 요청받았어도 한 화면에 모아 보여주지 않는다.** 초안을 하나씩 보여주고
그 건에 대한 개별 승인을 받은 뒤에만 그 건을 생성한다. 승인이 나면 다음 건의 초안을 이어서
보여준다 — 나머지 건들의 승인을 앞서 받은 것으로 넘겨짚지 않는다.

**요약·설명이 아니라 title/label/body 전체를 그대로(본문은 마크다운 원문 그대로) 보여준다.**
본문을 요약하거나 항목별 설명으로 대체하지 않는다 — 본문이 실제로 등록될 내용이므로 전체를
봐야 승인이 의미 있다.

## 6. 생성

승인되면 아래 형식으로 생성한다. **assignee는 항상 작성자 본인(`@me`)으로 지정한다.**

```bash
gh issue create \
  --title "<제목>" \
  --label "<라벨>" \
  --assignee "@me" \
  --body-file <body-file>
```

`--label`은 4단계에서 실존이 확인된 값만 넣는다. 매칭되는 라벨이 없으면 `--label` 플래그를
생략한다.

Windows에서 `gh`가 PATH에 없으면 전체 경로를 사용한다.

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" issue create --title "<제목>" --label "<라벨>" --assignee "@me" --body-file <body-file>
```

## 본문 줄바꿈 규칙

GitHub 이슈/PR 본문은 일반 마크다운과 달리 **단일 줄바꿈도 실제 줄바꿈(<br>)으로
렌더링된다.** 문장을 중간에서 엔터로 감으면 화면에서 문장이 뚝뚝 끊겨 보인다.

- **한 문단은 한 줄로 쓴다.** 아무리 길어도 문장 중간에 엔터를 넣지 않는다.
- 문단 구분은 빈 줄로만 한다.
- 줄바꿈은 의도된 곳에만 쓴다: 목록 항목, 표, 코드블록, 제목.

## 톤

담백하게 작성한다. 과장된 수식어, 완료됐다는 식의 서술을 쓰지 않는다. 인증 필요 여부,
기준 API spec/ERD 문서, 통과해야 하는 테스트를 명시한다.

## 금지 사항

- 범위 없이 "이슈 만들어줘"라고만 하면 바로 생성하지 않는다.
- template placeholder를 그대로 남기지 않는다.
- 실제로 존재하지 않는 라벨을 임의로 지정하지 않는다.
- assignee 없이 이슈를 생성하지 않는다.
- 애매한 응답을 승인으로 넘겨짚고 이슈를 생성하지 않는다.
- 본문을 요약해서 보여주고 승인받지 않는다 — 전체 본문 원문을 보여준다.

## 기존 이슈 수정

이슈 수정 요청을 받거나, 신규 생성 전 확인에서 겹치는 기존 이슈를 발견해 수정으로
전환하는 경우 이 절차를 따른다. 이슈 수정은 단순 텍스트 변경이 아니라 설계 변경이다.

1. **연관 산출물 파악** — 수정 전에 먼저 확인한다.
   - 이슈 번호 기반 브랜치 존재 여부 (`git branch -a | grep #<번호>`)
   - plan 문서: `product-service/docs/plans/`에서 이슈 번호/주제로 검색
   - spec 문서: `docs/superpowers/specs/`(로컬)에서 동일 검색
   - 열려 있는 PR (`gh pr list --search "#<번호>"`)
2. **이슈 수정안 승인** — 신규 생성과 동일하게 수정 후 본문 전문을 그대로 보여주고
   명확한 승인을 받은 뒤에만 `gh issue edit`을 실행한다.
3. **설계 문서 동기화** — 이슈 변경이 설계(범위·API 계약·데이터 구조·처리 방식)에
   영향을 주면, 1에서 찾은 plan/spec 문서의 수정안도 diff로 보여주고 개별 승인 후
   함께 수정한다. 이슈만 고치고 설계 문서를 방치하지 않는다.
4. **진행 중 구현 영향 보고** — 해당 브랜치에 이미 구현이 진행됐으면, 영향받는 코드
   범위를 보고하고 재작업 여부를 사용자가 결정한 뒤 진행한다.
5. **PR 갱신** — 열려 있는 PR이 있으면 본문(변경 요약·체크리스트)도 승인 후 갱신한다.

설계 문서를 먼저 고친 경우도 역방향으로 동일하다 — 설계가 바뀌면 이슈 본문도 함께
동기화한다. 단순 조회("이슈 내용 보여줘")는 이 절차 대상이 아니다 — 수정이 시작되는
순간부터 적용한다.
